# instrumentation.ts is the sole armer of background loops

Background loops (queue worker, reply sync, bounce watch, sender health, avatar prefetch) are started only from `instrumentation.ts` at server boot — never as a side effect of importing their module. The queue worker previously also self-started at module bottom, which forced a convention opposite to every other loop (its module scope could never reset the `started` flag, because any route bundle importing it would otherwise retire the live loop mid-send and double-send) — a rule that lived in a 10-line comment and made the file HMR-hostile. With one armer, that hazard's precondition is gone and all loops share one lifecycle convention: module scope resets nothing and starts nothing; `start*()` bumps the generation; an explicit stop exists for tests. Any future loop must follow the same rule rather than self-starting.

One named exception to "module scope does nothing": a loop module may publish its per-tick function onto the shared state (`state.tick = tick`) at module scope. That mutation retires nothing and arms nothing — the one running loop simply calls through the pointer — and it is the only dev-HMR path that exists, because Next caches instrumentation's `register()` for the life of the server process, so a re-arm can never deliver new code. In production every module copy is built from the same source and the swap is behaviourally a no-op.
