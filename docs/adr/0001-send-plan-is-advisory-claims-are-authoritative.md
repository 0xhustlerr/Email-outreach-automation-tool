# The send plan is advisory; claims are authoritative

The send plan is one pure function that both the queue worker and the queue UI consume, so scheduling rules exist in exactly one implementation (previously the UI mirrored the worker's gates and the two drifted repeatedly). But the plan never *causes* a send: the worker still takes each item through a transactional SQL claim, which re-validates eligibility — including facts only the database can answer at that instant, such as whether the contact has replied. We chose this over letting the plan drive sends directly because a plan computed from a snapshot can be stale by execution time, and acting on it without re-validation reopens the double-send hazard the claim design exists to prevent. Consequence: plan entries are honest predictions, not promises — bump ETAs are conditional ("unless the contact replies"), and any disagreement between plan and claim resolves in the claim's favour.
